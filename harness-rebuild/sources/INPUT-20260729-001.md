# ADR: Papertable 判决簿（Verdict Ledger）

## 1. 背景与问题

Papertable 现有 Harness 已解决"AI 怎样可靠地围绕资料回答"（native tools、只读检索、引用资格、宿主冻结 scope）。本次决策解决的是另一个问题：

**干净上下文的代价是失忆，失忆的代价是平庸复发。**

- 改道/发散/新窗口靠砍掉污染历史获得干净上下文，但同时砍掉了用户此前的否决判断；
- 于是模型在每个新的干净窗口里，会重新收敛回用户早已否决的平庸方向（AI 约 99% 的回答是平庸的，用户的追问本质是对抗这种过早收敛）；
- 用户被迫在每个新窗口重打一遍同样的仗。

## 2. 已确认前提（全部来自用户多轮确认，非推断）

1. 用户的内化终点是**复用进工作**（产品决策、开发），不是记忆掌握。
2. **人是索引，AI 是存储和读者**：用户让 AI 检索笔记仓库的前提是"自己能记住大概的范围"；用户不会绕过 AI 亲眼翻存量。
3. 脑内索引以**概念**为单位，靠**追问链**（对抗 AI 过早收敛的系列追问）登记；只问一次、无追问的内容大概率遗忘。
4. **1% 命中自编码**：真正解决问题的回答（灵感级）用户不会忘，靠外部刺激（如刷到相关视频）自然复活，无需产品捕获仪式。
5. **"索引在、存储丢"不是损失**：只要有印象，旗舰模型可快速重推出等价物。
6. **系统真正需要替用户记住的是"用户否定过什么"**——否决对象是平庸方向，平庸的东西人脑不会主动编码，但系统捕获成本极低。
7. 模型天花板问题不存在：用户始终使用最前沿旗舰模型，且常拿同一问题问多个旗舰模型。
8. AI 代写笔记路线已被实践证伪：笔记越写越多、用户不知其内容、有价值内容被活埋。

## 3. 决定

**Papertable 的耐久层是一份判决簿：只持久化用户判决，其余一切是耗材。**

判决只有两种，均只能由用户动作产生：

| 类型 | 含义 | 产生时机 |
|---|---|---|
| 墓碑 | 用户否决的方向："此思路平庸/错误，不要再收敛回来" | 改道时 |
| 金子 | 用户认可的 1% 命中：结论 + 用户亲手措辞的概念把手 | 用户对某轮回答显式"采纳"时 |

**判决簿的读者是 AI，不是人**：宿主把项目内相关判决注入每个新开的干净上下文（新卡片、新分支），实现"干净但不失忆"。这从根上绕开"AI 写笔记人不读"的病理——判决簿不是给人读的笔记，是给模型的上下文原料。

## 4. 机制细节

### 4.1 墓碑生命周期
1. 用户执行改道（现有语义不变：砍掉分支点之后的历史）；
2. AI 从被砍掉的历史起草**一句话**墓碑草稿：`用户否决了 <方向X>，因为 <理由Y>`，状态 `proposed`；
3. 用户过目：一键确认或改写一行 → `confirmed` 入簿；不理会则不入簿、随耗材蒸发；
4. 仅 `confirmed` 条目参与注入。

### 4.2 金子生命周期
1. 用户对某轮回答执行"采纳"（新增的显式动作，可复用/扩展现有 favorite 交互）；
2. 用户用自己的话铸一个概念把手（一句话以内，必须出自用户之手——继承"亲手写过一行才算数"原则）；
3. 结论 + 把手入簿，状态直接 `confirmed`（因为把手本身就是用户确认）。

### 4.3 注入
- 时机：buildContext 拼装每个新卡片/新分支的上下文时；
- 范围：宿主按**项目 + 概念匹配**冻结，模型不能自选或扩大范围；
- 形式：system 层的紧凑约束块，每条判决一行，token 成本可忽略；
- 提示词语义：金子作为已确认结论/锚点；墓碑作为负面约束（"避开这些已否决方向，但不过度回避"——此处是提示词最可能失败的点，列入验证）。

### 4.4 呈现（重新进入）
- 重新进入项目的默认视图 = 判决簿（金子 + 墓碑），树的其余部分折叠为可展开的耗材；
- 不做按时间平铺全部节点的默认视图。

## 5. 数据状态与晋级关系

- 探索痕迹 / AI 解释：无认识论状态字段，可归档可蒸发，**永不自动晋级**；
- 判决：`proposed`（仅墓碑草稿有此态）→ `confirmed`；
- "掌握"：**不建模**。唯一被承认的掌握证据是复用——判决被后续上下文命中注入的次数（可统计，不做考试/复习机制）。

## 6. 存储：从第一天起外接 MemOS

- 判决簿落在 MemOSjyi 的独立 Cube（建议名 `papertable-verdicts`），Papertable 经 API 读写；不新建本地判决表作为真值；
- 路线：**先外接、后内嵌**——外接期在真实负载下打磨治理规则，内嵌只是搬迁不是重写；
- 分工：
  - 宿主（Papertable）强制：铸币权（只有用户确认动作能产生 confirmed 条目，模型无权写入或伪造）、注入范围冻结、一行长度上限；
  - MemOS 负责：存储、检索、治理（去重、时效判断、supersede 标记）；
  - 治理红线：对判决**只许 supersede 降级标记，不许静默删除**——墓碑的失效本身是信息。

## 7. 宿主代码强制 vs 提示词负责

| 宿主代码强制 | 提示词负责 |
|---|---|
| confirmed 条目的唯一产生路径是用户动作 | 墓碑一句话草稿的起草质量 |
| 注入范围（项目+概念）冻结 | 模型如何使用负面约束（避开但不过度回避） |
| 条目一行长度上限 | 金子锚点在回答中的复用方式 |
| 改道砍历史的既有语义不变 | |
| supersede-only，禁止静默删除 | |

## 8. 验证：事件门 + 半天迭代（非日历门）

判死单位是"连续 N 版迭代无改善"，不是天数。三判据：

1. **约束无效（最致命，当天可测）**：挑 10 个用户否决过方向的老问题，注入判决 / 不注入各问一遍干净窗口做 A/B；"收敛回已否决方向"的复发率未减半 → 当天改注入措辞重测；连续 3 版无改善才判死。
2. **机制太重**：每累计 20 次改道结算：confirmed 墓碑占比 < 30% → 确认交互仍太重，下一版减一步交互再跑 20 次。
3. **起草太烂**：前 10 条 AI 起草墓碑中被大改或放弃 > 5 条 → 当天换起草提示词重跑。

## 9. 明确不做

- 不做知识图谱；
- 不做复习/间隔重复/考试系统；
- 不新增卡片类型（判决不是卡片，是上下文原料）；
- 不做"AI 自动提取收获/自动写笔记"；
- MVP 不内嵌 MemOS（外接 API 即可）；
- 不做工程化留白/故意不讲透（已被用户否决：那只是给平庸镀金）。

## 10. 本决策讨论中被否决的备选（墓碑记录）

| 被否决方向 | 否决理由 |
|---|---|
| 记忆/复习路线（费曼复述、隔天回忆、间隔复习） | 用户内化终点是复用非记忆；"AI 认可复述"不等于掌握 |
| 工程化留白（回答故意留缝隙诱发追问） | 用户追问由对抗平庸驱动，不是由缝隙驱动；留白=平庸镀金 |
| 采金登记仪式（命中时强制捕获） | 1% 自编码不会忘，捕获仪式解决不存在的问题（"采纳"仅为供 AI 复用而入簿，非防遗忘） |
| 直接内嵌 MemOS | 先外接打磨治理规则，成熟后内嵌 |
| 14 天日历门验证 | AI 半天一版、日输入海量；慢周期做废绕不回去，改事件门 |
| 呈现侧减法依赖 AI 判断重要性 | AI 判断"什么有价值"复活老病理（又一批用户不知内容的 AI 产物） |
| 把"笔记存在"当作"用户掌握" | 未登记进脑内索引的存量功能性死亡 |

## 11. 与现有代码的接触点（供实现参考）

- `edges` 表（type=branch 的改道边）：墓碑起草的触发点与来源（被砍历史 = `context_cutoff_turn_id` 之后的轮次）；
- `Turn.favorite` / 新增"采纳"动作：金子入口；
- `Card.concepts` / `origin: "concept-promotion"`：概念匹配注入的既有地基（注意：AI 提取的 concepts 仅作检索匹配用，不代表用户掌握）；
- `buildContext`（`BuiltContext.system` / `provenance`）：注入点，判决应以独立 `ContextProvenance` 种类标注（如 `verdict`），保持可审计；
- MemOSjyi：新增 `papertable-verdicts` Cube 与备份纳管（沿用 `tools/memos_backup.py` 的快照/校验/恢复约定）。

## 12. 候选产品记忆（已确认写入）

> Papertable 耐久层采用"判决簿"：只持久化用户判决——否决的方向（墓碑，改道时 AI 起草一行、用户确认入簿）与认可的 1% 命中（金子，用户亲手铸概念把手）。判决簿从第一天起外接 MemOS（独立 Cube），铸币权与注入范围由宿主强制，MemOS 负责存储与治理（只许 supersede 标记，不许静默删除），验证顺手后再内嵌。判决注入每个新干净上下文，实现"干净但不失忆"。探索痕迹是耗材，不建模"掌握"，复用次数是唯一掌握证据。验证按事件门+半天迭代：注入 A/B 当天可测，复发率减半、20 次改道确认率≥30%、起草改写率<50%，连续多版无改善才拆机制。定位为解决自身痛点的个人项目，非产品。
